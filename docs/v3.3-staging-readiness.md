**Audit date:** 2026-10-28. **Branch audited:** `chore/v3.3-staging-readiness` (identical to
`v3.3-dev` at commit `14c3bf0`). **Nature of this document:** an operator/founder runbook — what

## 1. Current architecture summary

Interval is an offline-first Expo/React Native app with three AWS environments
(`us-east-2`): **Production** (grandfathered, not CDK-managed), **Development** and **Staging**
(both `infra/`-managed CDK stacks, deployed and founder-QA verified for their *baseline* sync/auth
flow). Core entities (deck/card/session) use soft-delete tombstones and a push/pull sync protocol
against `Interval_Records`/`Interval_Changes`. `v3.3-dev` added, since the v3.2 freeze baseline:
FSRS scheduling + `ReviewEvent` sync, `GeneratedCardProvenance` sync, Source Structure +
structure-aware generation scopes, whole-source multi-batch AI generation, the AI evaluation
harness, a real Bedrock/Nova-2-Lite backend (Development-only), AI generation rate limiting, AI
request idempotency, and sync cursor hardening (`Interval_ChangeStream`). See
`CLAUDE.md`'s Documentation Hierarchy (items 28–37) for the authoritative per-feature detail; this
runbook does not restate it, only its *readiness* implications.

**The two systems this audit centers on are both fully implemented, fully unit-tested, and fully
inert** — neither has changed live behavior anywhere, by design:

- **Sync cursor hardening** — fixes a real, confirmed correctness bug (an offline/backdated write
  could be permanently excluded from a device's future incremental pulls). Dual-mode
  (`SYNC_CURSOR_MODE legacy|v2`, `SYNC_PUSH_MAINTENANCE true|false`), fail-closed to
  `legacy`/`false` in committed `infra/cdk.json`. **Not deployed anywhere.**
- **AI request idempotency** — adds durable, replay-safe provider-request identity (claimed →
  provider_started → succeeded/failed/unknown), reusing the existing 20/day quota atomically.
  Three modes (`legacy|optional|required`), fail-closed to `legacy` normally but to the *strictest*
  mode (`required`) on an unrecognized value — a deliberate, unusual direction, confirmed in code.
  **Not deployed anywhere.** Production and (for the AI Lambda itself) Staging are not
  instantiated at all for this feature.

## 4. Sync cursor hardening — rollout, verified against code

**Full design, failure modes, and the exact command-level sequence already live in
`docs/sync-cursor-semantics.md`'s "Rollout: exact command-level sequence" section — this runbook
does not duplicate it, it summarizes and confirms it was independently re-verified against the
actual committed code (not re-derived from the doc) during this audit.**

### Code verification result: **CLEAN — no discrepancies found**

An independent read-only audit of `infra/lib/interval-sync-stack.ts`, `infra/cdk.json`,
`backend/lambdas/sync-push/lib.mjs`, `backend/lambdas/sync-pull/lib.mjs`, and
`backend/scripts/backfill-change-sequence.mjs` confirmed every claim in the design doc exactly:
the `Interval_ChangeStream` table (PK string, `seq` Number sort key, `PAY_PER_REQUEST`,
`AWS_MANAGED` encryption, `pointInTimeRecovery: false`, per-environment removal policy), the
fail-closed context resolvers (`resolveSyncCursorModeContext`/`resolveSyncPushMaintenanceContext`
in CDK; `resolveSyncCursorMode`/`resolveMaintenanceMode` in the Lambda — both default to the safe
value for anything but the exact expected literal), the IAM grants (union of legacy + v2 needs, no
`/index/*` ARN anywhere — confirming the abandoned GSI approach left no trace), the transactional
`assignSequenceAndAppendChangeLog` (3-action `TransactWriteItems`, `MAX_SEQUENCE_ASSIGNMENT_ATTEMPTS
= 10`), `ConsistentRead: true` on both v2 query modes in `sync-pull`, and the backfill script's
safe dry-run default (`--execute` required to mutate), `DEFAULT_MAX_PASSES = 5` convergence loop,
and non-zero exit on any non-convergence or integrity mismatch. `infra/cdk.json`'s committed
context is confirmed literally `legacy`/`false` for both Development and Staging.

**Tests:** `npm run test:sync` → **106/106 pass**, covering `sync-push/lib.test.mjs`,
`sync-pull/cursorHardening.test.mjs` (reproduces the original bug and the fix across three entity
types), `sync-pull/lib.test.mjs`, and `backfill-change-sequence.test.mjs`. `cd infra && npx tsc
--noEmit` → clean.

### Exact rollout sequence (Development first; repeat with `staging`-prefixed names for Staging
only after Development's multi-device validation passes)

```sh
cd infra

# 1. Deploy infra + dual-mode Lambda code — INERT (committed context is already legacy/false).
npx cdk deploy IntervalDevelopmentStack
# --- Verify: ordinary sync still works exactly as before this deploy. ---

# 2. Freeze sync-push. sync-pull is unaffected and keeps serving legacy reads.
npx cdk deploy IntervalDevelopmentStack -c developmentSyncPushMaintenance=true
# --- Verify: a push now returns 503 {"ok":false,"error":"maintenance","retryable":true}.
#     A pull still returns 200 with existing history. ---

# 3. Run the backfill — this also runs its own convergence-verification loop and
#    post-convergence integrity check, and exits non-zero rather than ever reporting false success.
node backend/scripts/backfill-change-sequence.mjs \
  --table interval-dev-changes --stream-table interval-dev-change-stream \
  --region us-east-2 --execute
# --- Verify: final line is "[backfill] integrity verified ... Safe to deploy the new Lambda code
#     next." and exit code is 0. Do not proceed otherwise. ---

# 4. Cut over SYNC_CURSOR_MODE to v2 — WHILE STILL FROZEN.
npx cdk deploy IntervalDevelopmentStack \
  -c developmentSyncCursorMode=v2 -c developmentSyncPushMaintenance=true
# --- Verify: a pull against a known test account returns a numeric cursor + expected history. ---

# 5. Unfreeze.
npx cdk deploy IntervalDevelopmentStack \
  -c developmentSyncCursorMode=v2 -c developmentSyncPushMaintenance=false

# 6. Promote into infra/cdk.json: "developmentSyncCursorMode": "v2" (leave maintenance "false").
#    Commit this change so a future plain `cdk deploy` can never silently revert it.

# 7. Founder QA: ordinary incremental sync, two-device convergence, Force Resync (§11).
```

### Failure / rollback plan

| Failure point | What happens | Safe response |
|---|---|---|
| Backfill fails to converge (step 3) | Script exits non-zero, prints which rows are still unmigrated; **no Lambda mode has changed yet**, maintenance freeze is still active | Confirm the freeze is actually in effect (check for a stray un-frozen deploy or a second environment's Lambda pointed at the same table), re-run the backfill. Never proceed to step 4 on a non-zero exit. |
| Integrity check mismatches (step 3) | Same as above — the script's own post-convergence row-count check failed | Investigate before re-running — do not force past this with a manual table edit. **Never manually delete or edit rows in `Interval_Changes`/`Interval_ChangeStream` to "fix" a mismatch** — this is the one thing that must never be done; let the backfill's own idempotent re-run logic reconcile it. |
| v2 pull fails during smoke test (step 4) | Still frozen — no user-visible impact yet, no new write has occurred under v2 | Revert cursor mode back to legacy while investigating: `npx cdk deploy IntervalDevelopmentStack -c developmentSyncCursorMode=legacy -c developmentSyncPushMaintenance=true`, then unfreeze once reverted. This is safe because the write freeze means no new data was created under the broken v2 path yet. |
| Problem discovered AFTER unfreeze + real v2 writes have landed | **Rollback to legacy is no longer simply safe** — legacy mode's `appendChangeLogLegacy` does not know about `Interval_ChangeStream`, so a v2 write made after unfreeze has no legacy-shaped row; reverting the cursor mode would make `sync-pull`'s legacy path blind to it | Do not revert `SYNC_CURSOR_MODE` back to `legacy` once real v2 writes exist. Fix forward instead (patch the v2 code, redeploy v2) — this is explicitly called out in `docs/sync-cursor-semantics.md`'s "Known limitations": there is no automated rollback-after-cutover path, by design. |
| Any step: Lambda misbehaves generally after a deploy | — | Redeploy the previous Lambda revision via CDK. **Never `cdk destroy IntervalDevelopmentStack`** — that deletes Development's Cognito accounts + DynamoDB data, an environment teardown, not a rollback. |

**Data that must NEVER be manually deleted:** `Interval_Changes`, `Interval_ChangeStream`, the
per-user `SEQ#COUNTER` row, or any row the backfill script touches. The backfill is designed to be
safely re-run (already-migrated rows are skipped), which is the correct recovery path for almost
every failure above — manual data surgery is never required and risks silently breaking the
write-order invariant the whole fix exists to guarantee.

`PAY_PER_REQUEST`, `AWS_MANAGED` encryption, created **unconditionally for both environments**);
`infra/cdk.json`'s `developmentAiIdempotencyMode`/`stagingAiIdempotencyMode` both literally

### Exact rollout sequence (Development; Staging's AI Lambda does not exist yet — see note below)

```sh
# Only after explicit deployment approval.

# 1. Provision optional mode — table/IAM/code deploy together (no "infra only" step exists).
cd infra
npx cdk deploy IntervalDevelopmentStack -c developmentAiIdempotencyMode=optional
# Persist "developmentAiIdempotencyMode": "optional" in infra/cdk.json once deployed and confirmed.

# 2. Release the mobile client that sends generationAttemptId + requestId.
#    New client -> old backend stays contract-v1 compatible (no replay guarantee).
#    New backend optional -> old client stays compatible (keyless clients get legacy admission).

# 3. Verify exact replay, conflicts, quota and lease behavior (Founder QA checklist A-J,
#    docs/ai-request-idempotency.md's "Validation and Founder QA" section). Then:
npx cdk deploy IntervalDevelopmentStack -c developmentAiIdempotencyMode=required
# Persist "developmentAiIdempotencyMode": "required" in infra/cdk.json once verified.
# Old (keyless) clients are intentionally refused only from this point forward.
```

**Staging note:** setting `stagingAiIdempotencyMode` deploys the *storage declaration* only —
it does **not** create a Staging AI HTTP Lambda/route (none exists in `infra/lib/
interval-sync-stack.ts`'s Staging branch) and does **not** enable real AI on Staging. Staging's
app continues calling the local mock provider regardless. Live Staging HTTP replay QA is not
possible until a separate, explicitly-approved Staging AI endpoint rollout happens.

### Failure / rollback plan

| Failure point | What happens | Safe response |
|---|---|---|
| Optional-mode deploy misbehaves | Keyless clients still get legacy admission (unaffected); keyed clients may see conflicts/503s | Redeploy previous revision, or `-c developmentAiIdempotencyMode=legacy` to fully disable — safe at this stage since no client depends on replay protection yet |
| Required-mode rollback attempted | **Not safe while protected in-flight operations exist** — an old (keyless) client would be refused outright the moment `required` is active, and reverting to `legacy`/`optional` while a client *expects* replay protection removes that guarantee silently | Only roll back `required` → `optional`/`legacy` during an operational pause/drain longer than the 60-second lease + Lambda timeout window, with explicit acceptance that in-flight protection is lost for that window |
| Ambiguous/unknown claim state found in the table | By design, **never automatically reclaimed or reused** | Never manually delete an ambiguous row to "unstick" it — an unknown-outcome record is a deliberate safety fence, not a bug; a full restart (new UUIDs) is the user-facing recovery path, consuming a new quota unit as designed |
| Quota/table cleanup question | — | **Prefer no manual cleanup at all.** Records expire via native DynamoDB TTL (24h logical eligibility, asynchronous physical deletion per AWS's own TTL semantics) — this is sufficient; manual deletion risks removing a record that is still within its legitimate 24h replay window for a legitimate retry. |
| "Can old clients still function?" | Yes in `legacy` and `optional` (keyless clients get ordinary admission, no replay guarantee); **no** in `required` (missing request ID is rejected outright) | This is the exact, deliberate tradeoff `required` mode exists to make — do not activate `required` until the client rollout in step 2 above is confirmed complete |

## 10. Development device QA matrix

**Auth:** fresh sign-up → sign-in; existing account sign-in; kill & relaunch (token refresh/
session restore); sign out.

**Sync:** Device A creates/edits/deletes a deck → Device B receives it; Device A edits offline,
Device B edits a different entity, reconnect A → both converge; a backdated/offline-created
record arrives after the cursor has advanced (the exact bug class §4 fixes — meaningful to test
only AFTER the v2 cutover); tombstone delete → restore; `ReviewEvent` sync (review a card on two
offline devices before sync, confirm both events survive); `GeneratedCardProvenance` sync after a
saved generation.

**Scheduling:** Again/Hard/Good/Easy on a revealed answer; Study Due Cards queue reflects due/new
counts correctly cross-device; deterministic replay (same review history recomputes the same
`CardSchedulingState` on a second device).

**Sources:** TXT, PDF, DOCX, XLSX attach + reader open; archive/restore a source; "Open original"
handoff.

**AI:** Automatic (bounded) generation; Entire-source whole-source multi-batch generation; DOCX
heading structure-node scope; XLSX worksheet structure-node scope; a deliberately tiny source
(insufficient-distinct-content honest reporting); cancel mid-generation; retry after cancel
(confirm it's a full restart, new quota unit); hit the daily rate limit; **idempotency replay**
(requires optional/required mode actually deployed first — not testable today); duplicate-key
conflict (same requestId, different content — expect 409); ambiguous-outcome simulation (kill the
app mid-request if practical, confirm the UI reports an honest "unknown" rather than a false
success).

**Coverage:** generated cards affect Source Coverage only after explicit Save (never on draft
generation alone); delete a card/deck and confirm coverage updates; restore and re-confirm;
cross-device coverage consistency after `GeneratedCardProvenance` sync lands on a second device.

**Import:** CSV, TSV, a genuinely Quizlet-exported file, and one deliberately malformed file (
confirm a clean rejection, not a crash or partial import).

**Localization:** English, Spanish, Arabic (RTL chrome, LTR English body text inside an Arabic
shell), one CJK locale (Japanese or Korean — confirm no text truncation/overflow in the structure
picker or generation progress copy).

**Accessibility:** VoiceOver pass over the Generate options screen, the `StructureNodePicker`
(breadcrumb/positional-disambiguation announcements), and the multi-batch generation progress
copy — none of this has been device-verified yet per `CLAUDE.md`'s tech-debt list.

## 11. Multi-device QA (mandatory before Production)

Two physical/simulator devices, same account, both pointed at Development (repeat against
Staging once its own rollout completes).

| Step | Action | PASS condition |
|---|---|---|
| 1 | Device A creates a deck+cards, generates via AI, saves | Device B receives the deck, cards, AND `GeneratedCardProvenance` entries after its next pull |
| 2 | Device A reviews cards (Again/Good/etc.) while Device B is offline | Device B comes online, pulls, and its recomputed `CardSchedulingState` matches what Device A would compute from the same merged `ReviewEvent` history |
| 3 | Both devices review the SAME card independently while BOTH offline, then both reconnect | Both review events survive (identity-based merge, never one overwriting the other) |
| 4 | Device A makes an edit, waits long enough for Device B's cursor to advance past it via unrelated activity, THEN pushes the edit "late" | **Only valid as a real test once §4's v2 cutover has happened** — pre-cutover, this is the exact bug that can legitimately fail; post-cutover, Device B must receive it on its next incremental pull, not just a Force Resync |
| 5 | Device A deletes a deck; Device B restores... wait, decks don't restore, but a Library source does | Device A archives/deletes a Library source, Device B sees the tombstone; restore on A, B sees it reappear |
| 6 | Both devices generate from the same Library source independently | Source Coverage converges to the same answer on both after provenance sync, no double-counting |

**PASS condition for the whole checklist:** no silent data loss, no permanently-diverged state
between the two devices, and (for step 4 specifically) no record that one device can see and the
other can never receive short of a full Force Resync.

## 12. Network failure QA

- Airplane mode engaged immediately before tapping Generate → honest "offline" state, no crash, no
  false "generating" spinner.
- Network lost mid-HTTP-request during generation → client reports an honest failure/unknown
  state (never a false success); no quota is silently re-consumed by an automatic retry (there is
  none — confirmed in code, `docs/ai-request-idempotency.md`'s "no automatic HTTP retry").
- Retry the SAME logical request after a network loss, once idempotency is actually deployed in
  `optional`/`required` mode → exact replay if the original call had actually completed
  server-side; `request-in-progress`/`request-outcome-unknown` otherwise — not testable until §5
  ships.
- Cancel mid-batch (whole-source generation) → the in-flight request cannot be interrupted (no
  `AbortSignal` exists, documented limitation), but its result must be discarded and never
  published to review.
- App backgrounded during a batch → on foreground, confirm no duplicate publication and no stuck
  "generating" state.
- Simulate backend `503` (maintenance mode, once §4's freeze step is exercised, or a forced
  daily-limit `429`-equivalent) → client shows the mapped, provider-neutral copy, never a raw
  error string, never "idempotency" in user-facing text.
- `request-in-progress` / `request-outcome-unknown` (once idempotency is deployed) → confirm the
  exact copy shown matches the 13-locale mapping and never implies success.

No proxy/network-shaping tooling beyond airplane mode and app backgrounding is required or
assumed available for this list.
